# Sprint 1 — Bank v1 (in-memory, однопоточная база)

## BANK-1: Доменная модель BankAccount
Описание: класс счёта с уникальным идентификатором и балансом.
Критерии приёмки:
- Идентификатор неизменяем после создания.
- Баланс не может быть отрицательным в любой момент времени.
- Есть методы для получения текущего баланса.

## BANK-2: Операции deposit / withdraw / transfer (однопоточный сценарий)
Описание: базовые операции над счётом и перевод между двумя счетами.
Критерии приёмки:
- withdraw при недостатке средств выбрасывает осмысленное исключение, баланс не меняется.
- Отрицательная или нулевая сумма операции отклоняется.
- transfer либо выполняется целиком (списание + зачисление), либо не выполняется вовсе.
- Проверено вручную (через Main/логи) на сценариях: успешный перевод, недостаток средств, некорректная сумма. Автотесты — см. BANK-8.

## BANK-3: Потокобезопасность переводов
Описание: те же операции, но при конкурентных вызовах из многих потоков.
Критерии приёмки:
- Ни один перевод не должен «потерять» или «размножить» деньги при параллельном выполнении.
- Система не зависает (deadlock) при большом количестве одновременных переводов между произвольными парами счетов.
- Есть стресс-сценарий (можно без JUnit, обычным main/раннером): N потоков делают случайные переводы между M счетами; после завершения суммарный баланс всех счетов равен начальному.

## BANK-4: Generic-репозиторий счетов
Описание: обобщённое хранилище `Repository<T, ID>` с реализацией для BankAccount.
Критерии приёмки:
- Интерфейс репозитория параметризован типом сущности и типом идентификатора (не завязан конкретно на BankAccount).
- Реализация потокобезопасна для конкурентного доступа.

## Sprint 2 — Bank v2 (домен и многопоточность, без SQL/Spring/JUnit)

## BANK-9: История транзакций и типы счетов
Описание: модель `Transaction` (id, accountId, type — DEPOSIT/WITHDRAW/TRANSFER_IN/TRANSFER_OUT, amount, timestamp, related accountId для переводов), которая пишется при каждой операции. Плюс иерархия счетов: базовый `BankAccount`, `CheckingAccount` (овердрафт до лимита) и `SavingsAccount` (лимит на снятие за период, начисление процентов).
Критерии приёмки:
- Запись транзакции в историю происходит атомарно вместе с изменением баланса — под тем же локом, без риска рассинхронизации при конкурентном доступе.
- История счёта возвращается наружу как неизменяемая копия (защита от изменения извне).
- `CheckingAccount`/`SavingsAccount` переопределяют бизнес-правила (овердрафт/лимит снятия) без дублирования общей логики `transfer`/`deposit`/`withdraw`.

## BANK-10: Пакетная обработка переводов через ExecutorService
Описание: заменить связку "ручной массив `Thread[]` + `join()`" (как в стресс-тесте BANK-3) на обработку списка переводов через `ExecutorService` (fixed thread pool).
Критерии приёмки:
- Пул потоков создаётся с явным размером, корректно останавливается (`shutdown()` + `awaitTermination()`), без утечки потоков после завершения обработки.
- На выходе — сводка: сколько переводов выполнено успешно, сколько упало и по какой причине (без падения всего процесса из-за одного неудачного перевода).
- Те же гарантии корректности, что и в ручном стресс-тесте BANK-3 (суммарный баланс не меняется).

## BANK-11: Заморозка счёта и лимиты операций
Описание: статус счёта (`ACTIVE`/`FROZEN`/`CLOSED`) и дневной лимит на переводы (по сумме и/или количеству).
Критерии приёмки:
- Операция над замороженным/закрытым счётом отклоняется осмысленным исключением, а не тихо игнорируется.
- Проверка статуса и лимита выполняется атомарно вместе с самой операцией — не должно быть окна, где счёт "ещё активен" на момент проверки, но уже заморожен к моменту реального списания.
- Лимит по дню корректно сбрасывается/пересчитывается, без гонок при параллельных переводах одного и того же дня.

## BANK-12: Уведомления через Observer-паттерн
Описание: интерфейс `AccountObserver` (например, `onTransactionCompleted(Transaction)`), возможность подписать несколько наблюдателей на счёт или на сервис, автоматическое оповещение после успешной операции.
Критерии приёмки:
- Регистрация/оповещение наблюдателей потокобезопасны.
- Исключение в одном наблюдателе не должно ломать оповещение остальных подписчиков и не должно откатывать саму завершённую операцию.
- Минимум два разных наблюдателя для демонстрации (например, логирующий и алерт по низкому балансу).

## Sprint 3 — Bank v3 (переход на JDBC/PostgreSQL)

## BANK-5: Базовый JDBC-репозиторий счетов
Описание: CRUD поверх PostgreSQL через `BankAccountRepository` (save/get/delete), схема `schema.sql` (Class Table Inheritance для saving/checking-деталей), подключение через `ConnectionService`, docker-compose с Postgres.
Критерии приёмки:
- `save`/`get` корректно обрабатывают SQLState-коды (23505/23503/23502) осмысленными исключениями.
- `get()` восстанавливает верный подтип счёта (`BankAccount`/`SavingAccount`/`CheckingAccount`) по типу из `bank_account_type`.
- Везде `PreparedStatement` с параметрами, без конкатенации значений в текст запроса.
Статус: готово, прошло ревью.

## BANK-13: Фильтрованное чтение счетов
Описание: `getByPersonId(UUID)` и `getByType(AccountType)` в `BankAccountRepository` вместо неограниченного `getAll()`; `getAll()` кидает `UnsupportedOperationException`.
Критерии приёмки:
- Маппинг строки `ResultSet` в `BankAccount`/`SavingAccount`/`CheckingAccount` вынесен в один переиспользуемый метод и используется и в `get()`, и в обоих новых методах — без повторения `switch`.
- Оба метода фильтруют на уровне SQL, а не вычитывают всю таблицу и фильтруют в Java.

## BANK-14: Soft delete счёта через статус
Описание: `delete(UUID id)` в `BankAccountRepository` переводит счёт в статус `DELETE` (`UPDATE`), вместо физического `DELETE FROM bank_account`.
Критерии приёмки:
- Счёт со статусом `DELETE` не удаляется из таблицы физически, но перестаёт быть доступен для обычных операций.
- Отдельный метод жёсткого удаления не заводится — soft delete покрывает сценарий полностью.

## BANK-15: Persist изменений счёта (update) + отвязка начисления процентов
Описание: добавить `update(ID id, T item)` в `Repository<ID, T>`, реализовать в `BankAccountRepository` (обновление `balance`/`status` в `bank_account`, а для `SavingAccount` — ещё `withdraw_limit`/`date_last_accrual` в `saving_account_details`). Подключить вызовы `update()` в конце `transfer()`/`deposit()`/`withdraw()` в `BankAccountService`. Убрать вызовы `InterestAccrualService.accrueIfDue(...)` из этих трёх методов (сам метод `accrueInterestIfDue()` в `SavingAccount` и класс `InterestAccrualService` не трогать — понадобятся в BANK-16).
Критерии приёмки:
- После `transfer`/`deposit`/`withdraw` новый баланс/статус виден при повторном `get()` из БД, а не только в памяти процесса.
- Обновление баланса и запись `Transaction` в рамках одной операции либо применяются оба, либо ни один (реальная DB-транзакция на одном `Connection`, `commit`/`rollback`).
- `deposit()`/`withdraw()`/`transfer()` больше не вызывают `InterestAccrualService`.
